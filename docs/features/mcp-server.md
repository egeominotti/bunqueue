# Native MCP Server

> **Category:** Integration · **Source:** `src/mcp/index.ts`, `src/mcp/server.ts`, `src/mcp/serverFactory.ts`, `src/mcp/adapter.ts`, `src/mcp/transportConfig.ts`, `src/mcp/httpSecurity.ts`, `src/mcp/httpSessions.ts`, `src/mcp/httpTransport.ts`, `src/mcp/backend/**/*.ts`, `src/mcp/types/*.ts`, `src/mcp/httpHandler.ts`, `src/mcp/prompts.ts`, `src/mcp/resources.ts`, `src/mcp/tools/*.ts`, `src/mcp/toolSetup.ts`, `src/mcp/toolPolicy.ts`, `src/mcp/toolsets.ts`, `src/mcp/confirmGuard.ts`, `src/mcp/confirmImpact.ts`, `src/mcp/decisionModel.ts`, `src/mcp/workflow/*.ts`

## Purpose

The native MCP (Model Context Protocol) server exposes bunqueue to AI agents (Claude Desktop, IDEs, etc.). It ships as the `bunqueue-mcp` binary and uses the official `@modelcontextprotocol/sdk` to register **75 tools** (plus **3 optional workflow-engine tools**), **5 read-only resources**, and **3 prompt templates** that let an agent inspect, control, and consume from queues. The server talks to bunqueue either **embedded** (the shared in-process `QueueManager`) or over **TCP** to a remote broker, selected via `BUNQUEUE_MODE`. It serves one client over **stdio** (default) or several concurrent clients over the opt-in **Streamable HTTP** transport (`BUNQUEUE_MCP_TRANSPORT=http`). The `@modelcontextprotocol/sdk` (and its transitive `zod`) is an _optional_ peer dependency, so queue-only consumers never download it.

Agent-facing features are **opt-in** and change nothing unless their environment variables are set: toolset disclosure (`BUNQUEUE_MCP_TOOLSETS`), annotations plus confirmation of guarded calls (`BUNQUEUE_MCP_CONFIRM`), an optional decision model (`BUNQUEUE_MCP_DECISION_*`) in the SystemOne wire format shared by TypeSafe Jev, Cloudflare Clef / Clef-flash and self-hosted Kev 9B, Laya or DiffusionGemma Jev, and workflow-engine tools (`BUNQUEUE_MCP_WORKFLOW_DB`). See [Opt-in agent features](#opt-in-agent-features).

## Responsibilities & Scope

Owns:

- The `bunqueue-mcp` bin entrypoint and lazy SDK loading (`src/mcp/index.ts`).
- Process lifecycle: config validation, backend creation, transport start, startup line and graceful shutdown (`src/mcp/server.ts`).
- Building one fully registered `McpServer` (tools, opt-in features, resources, prompts), used once for stdio and once per HTTP session (`src/mcp/serverFactory.ts`).
- The opt-in Streamable HTTP transport: env parsing and validation (`transportConfig.ts`), bearer auth and DNS-rebinding guards (`httpSecurity.ts`), the session registry (`httpSessions.ts`) and the `Bun.serve` router (`httpTransport.ts`).
- The `McpBackend` contract and public adapter facade (`src/mcp/types/adapter.ts`, `types/jobOptions.ts`, `types/inspection.ts`, `src/mcp/adapter.ts`), the embedded and TCP implementations under `src/mcp/backend/`, and the mappers both share (`backend/jobOptions.ts`, `jobOptionsView.ts`, `dlqView.ts`, `dlqFilter.ts`, `limitsView.ts`, `serializers.ts`).
- The `HttpHandlerRegistry`, which spawns `Worker`s that auto-process jobs by issuing HTTP requests, embedded or against the remote broker in TCP mode (`src/mcp/httpHandler.ts`).
- Per-invocation error handling + telemetry recording (`withErrorHandler`, `mcpTracker`) and the shared zod input schemas (`tools/schemas.ts`, `tools/cronOptions.ts`).
- The tool policy table (toolset, MCP annotations, confirmation target for every tool), opt-in toolset disclosure, the confirmation gate and the optional SystemOne decision-model client (`toolPolicy.ts`, `toolsets.ts`, `confirmGuard.ts`, `confirmImpact.ts`, `decisionModel.ts`, wired by `toolSetup.ts`).
- Read and signal access to a workflow Engine's SQLite execution store (`src/mcp/workflow/`, `tools/workflowTools.ts`).

Does NOT own (delegated):

- Actual queue/job logic — delegated to [Core Queue Engine](./core-queue-engine.md) (embedded) or the [TCP Server Command Handlers](./tcp-server-handlers.md) (TCP mode).
- Wire framing/connection pooling — delegated to [Client Transport](./client-transport.md) (`TcpConnectionPool`).
- Flow tree construction — delegated to [FlowProducer & Job Dependencies](./flow-producer.md) (`FlowProducer`).
- Workflow execution — steps, compensation and recovery run only in the application's `Engine` ([Workflow Engine](./workflow-engine.md)); the MCP server reads the store and enqueues resume jobs.
- Cloud telemetry delivery — `mcpTracker` only buffers; delivery is owned by [bunqueue Cloud Dashboard Integration](./cloud-integration.md) (`CloudAgent`).
- TLS on the MCP HTTP port — not implemented; terminate TLS in a reverse proxy.

**Tool parameters and semantics.** zod validates every input before either backend runs; the numeric bounds mirror the broker's job-option validation (`tools/schemas.ts:15-23`), so embedded and TCP reject the same inputs. Every queue-name field (`queue`, flow `queueName`, worker `queues[]`, the optional webhook `queue`) and every job name is non-empty.

- **`jobs`.**
  - `add_job` and each `add_jobs_bulk` item take `queue`, `name`, `data` plus the shared options (`jobOptionsShape`, `schemas.ts:159-183`): `priority` (integer, ±1 000 000), `delay` (at most one year; a negative delay makes the job ready at once with a past run time, `jobDelayField`), `attempts` (integer 1–1000), `backoff` (a number 0–86 400 000 used as the exponential base — retry _n_ waits about base × 2^_n_, jittered, capped at 1 h — or `{ type: 'fixed' | 'exponential', delay, maxDelay? }`), `timeout` and `stallTimeout` (0–86 400 000 ms), `jobId` (custom id, 1–1024 characters of well-formed Unicode; it becomes the job id, ids are server-wide, a re-add while that job is unfinished returns the existing id), `deduplication` (`{ id, ttl? 1 ms–1 year, extend? (requires ttl), replace? }`, scoped to the queue), `removeOnComplete`, `removeOnFail` (booleans only), `durable`, `lifo`, `tags` (strings ≤ 256 chars). `groupId` is not exposed. Both backends map these through `backend/jobOptions.ts` (`toJobInput` for embedded push and TCP `PUSHB` items, where the custom id travels as `customId`; `toPushFields` for TCP `PUSH`, where it travels as `jobId`); undefined fields are omitted.
  - `add_jobs_bulk` is ordered, not atomic: invalid options reject the whole call, but a job the broker refuses during admission leaves the jobs before it added.
  - `get_job` returns the job with its `state` and its options (`backoff` always; `timeout`, `stallTimeout`, `lifo`, `removeOnComplete`, `removeOnFail`, `tags`, `deduplicationId` when set). `get_job_by_custom_id` finds only unfinished jobs (the custom id is released on completion or final failure; `get_job` still finds the finished job) and also reports `state` (TCP resolves it with an extra `GetState`, `backend/tcp/jobs.ts:92-97`).
  - `get_job_state`: `waiting`, `prioritized`, `delayed`, `active`, `completed`, `failed` (DLQ), `waiting-children`, or `unknown`.
  - `wait_for_job` (`timeoutMs` 100–30 000): `completed: true` immediately when the job already completed, `false` on timeout; an unknown job id is an error (`Job not found`) in both modes.
  - `get_progress` returns `{ progress, message }` for a job in any state (live value for an active job, stored value otherwise, `jobMgmtTools.ts:75-90`); `Job not found` only when the job does not exist.
  - `update_progress` (0–100, optional `message`); `get_job_logs`, `add_job_log` (`level` `info`/`warn`/`error`), `clear_job_logs` (`keepLogs` ≥ 0).
- **`job-control`.** `change_job_priority` takes a bounded integer `priority`. `move_to_delayed` (`delay` 0 to one year, like `change_delay`) reschedules an active, waiting, prioritized or delayed job; completed and failed jobs return `success: false`. `change_delay` changes a delayed job (TCP sends `ChangeDelay`). `discard_job` moves the job to the DLQ (retryable, so not guarded). `move_to_delayed`, `change_delay` and `discard_job` take no lock token, so a job locked by a pull with an `owner` is rejected with `Lock token required`.
- **`processing`.**
  - `pull_job` / `pull_job_batch` (`timeoutMs` 0–30 000, `count` 1–1000) take `owner` (1–256 chars) and `lockTtl` (1 000–86 400 000 ms, broker default 30 000; `lockTtl` without `owner` is an error, `consumptionTools.ts:19-25`). With an owner the job is locked and carries a `token` field (only when one was issued); pulled jobs report `state: 'active'`. An unrenewed lock expires: the job uses an attempt and is requeued or moved to the DLQ.
  - `ack_job` and `fail_job` take `token`; `fail_job` also takes `unrecoverable` (straight to the DLQ). A missing or wrong token is an error carrying the broker text (`Lock token required for job <id>`, `Invalid or expired lock token for job <id>`).
  - `ack_job_batch` (`jobIds` ≥ 1) and `job_heartbeat_batch` take `tokens` aligned with `jobIds` (`""` for a job pulled without an owner); a length mismatch is an error (`consumptionTools.ts:28-32`); one wrong token rejects the whole ack batch. `job_heartbeat_batch` returns `acknowledged`.
  - `job_heartbeat` takes `token`, which also renews the lock; a wrong or expired token returns `success: false`. Without the token the heartbeat succeeds but the lock is not renewed.
  - `extend_lock` requires `token` and `duration` (1 000–86 400 000 ms); `success: false` for a wrong token or an expired lock.
- **`queues`.**
  - `get_jobs` filters on `waiting`, `prioritized`, `delayed`, `active`, `completed`, `failed`, `paused`, `waiting-children` (`queueTools.ts:15-24`); `start`/`end` are integers ≥ 0 and default to 0/20. Each job carries its state.
  - `get_job_counts` (and `get_queue_stats`) return `waiting`, `prioritized`, `delayed`, `active`, `completed`, `failed`, `paused`, `waiting-children` with the paused view: a paused queue reports its ready jobs only under `paused`.
  - `count_jobs` is the sum of every `getJobCounts` bucket (`queueTools.ts:27-38`, computed in the tool for both backends); the backend `countJobs` method (queued jobs only) is no longer used by any tool.
  - `clean_queue` (`graceMs` ≥ 0, optional `state` `completed`/`failed`, optional integer `limit` ≥ 1): without `state` it cleans `completed`, then `failed`, and `limit` caps the combined total (`queueTools.ts:185-202`); the engine default is 1000 per state. It never passes an undefined state, which the broker treats as `waiting`. Returns `removed` and `ids`.
  - `drain_queue` removes waiting, prioritized and delayed jobs and returns `removed`; active, completed and failed jobs are kept.
- **`dlq`.**
  - `get_dlq` takes `limit` (integer 1–100, default 20), `offset` (integer ≥ 0) and `reason` (`explicit_fail`, `max_attempts_exceeded`, `timeout`, `stalled`, `ttl_expired`, `worker_lost`, `unknown`). It returns `{ queue, reason?, offset, count, hasMore, entries }`, oldest first; each entry is `{ job, reason, error, attempts, attemptCount, retryCount, enteredAt, lastRetryAt, nextRetryAt, expiresAt }` (see [Data Models](#data-models)). **Breaking:** the former top-level `jobs` array is gone; each job is inside its entry. `hasMore` comes from fetching `limit + 1` entries, so the DLQ is never counted in full.
  - `get_dlq_stats` returns `{ queue, total, byReason, pendingRetry, expired, oldestEntry, newestEntry }`; `byReason` carries every reason the engine reports.
  - `retry_dlq` (optional `jobId`; TCP sends it as `jobId`), `purge_dlq` and `retry_completed` (optional `jobId`) return counts.
- **`cron`.** `add_cron` takes `name` (non-empty), `queue`, `data`, `schedule` (5/6-field pattern or shortcut) or `repeatEvery` (integer ≥ 1), plus (`tools/cronOptions.ts:41-84`): `jobName`, `priority` (bounded integer), `timezone` (an IANA zone accepted by `Bun.cron.parse`; requires `schedule`, `cronOptions.ts:110-112`), `maxLimit` (integer ≥ 1), `immediately`, `skipIfNoWorker`, `preventOverlap` (default true), `skipMissedOnRestart` (default true), `deduplication` (mapped to `uniqueKey` + `dedup`), and job options `attempts`, `backoff`, `timeout`, `delay` (a negative delay is treated as 0), `stallTimeout`, `removeOnComplete`, `removeOnFail` (mapped to `jobOptions`). Re-adding a name replaces the schedule and keeps its run count; only one job per schedule is pending at a time under `preventOverlap`. `add_cron`, `list_crons` and `get_cron` return `SerializedCron` (with `jobName`, `priority`, `timezone`, `maxLimit`); the policy flags, deduplication and job options are applied but not echoed (see [Edge Cases](#edge-cases--failure-modes)).
- **`limits`.** `set_rate_limit` takes `limit` (integer ≥ 1) and `duration` (integer window in ms, 1 to one year, default 1000) and returns `durationMs`; the limiter is a continuously refilling token bucket. `set_concurrency` takes `limit` (integer ≥ 1). `get_queue_limits` returns `QueueLimits` (`{ queue, paused, rateLimit: { max, durationMs } | null, rateLimitTtlMs, rateLimited, concurrencyLimit, active, concurrencyMaxed }`).
- **`flows`.** `add_flow` (root and recursive `children`), `add_flow_chain` (`steps` ≥ 1) and `add_flow_bulk_then` (`parallel` ≥ 1, `final`) take a **strict** `opts` object (`flowTools.ts:28-47`): `priority`, `delay` (a negative delay is treated as 0), `attempts`, `backoff`, `timeout`, `jobId` (must be new and contain no `:`), `removeOnComplete`, `removeOnFail`, `lifo`, `stallTimeout`. `deduplication`, `tags` and `durable` are rejected (the broker rejects dedup in flows, stores no tags on flow jobs, and flows are always durable). `get_flow` takes integer `depth` ≥ 1 (default 10) and `maxChildren` ≥ 1.
- **`workers`.** `register_worker` (`queues` ≥ 1); `register_handler` (`url`, `method` `GET`/`POST`/`PUT`/`DELETE`, `headers?`, `body?`, `timeoutMs` 1 000–120 000, default 30 000).

- **`monitoring`.** `get_stats` shape differs by backend (see [Backend dispatch](#business-logic--control-flow)); `get_per_queue_stats` returns `waiting`, `prioritized`, `delayed`, `active`, `dlq` per queue; `get_memory_stats` returns the `QueueManager.getMemoryStats()` collection sizes in both modes.

## Data Models

All tool replies are `{ content: [{ type: 'text', text: JSON.stringify(...) }], isError? }`. The principal serialized shapes (see [data-model](../data-model.md) for the underlying `Job`/cron/DLQ/webhook types):

- `SerializedJob` — `{ id, name, queue, data, priority, state?, progress, attempts, maxAttempts, createdAt (ISO, or null), startedAt? (ISO) }` plus `SerializedJobOptions` (`backoff` always; `timeout`, `stallTimeout`, `lifo`, `removeOnComplete`, `removeOnFail`, `tags`, `deduplicationId` only when set). Built by `serializeMcpJob(job, state?)` (embedded, `backend/serializers.ts:8-23`) or `parseJob(job, state?)` (TCP, `backend/tcp/base.ts:86-105`); both stringify the `id`, convert timestamps with the range-checked `isoTime` (`workflow/jsonSafe.ts`: a legacy time outside the JavaScript Date range, such as a `timestamp` stored before the option bounds, is `null` instead of a thrown `RangeError` that failed the whole tool call), and use the shared `serializeJobOptions` (`backend/jobOptionsView.ts:34-48`). `state` is filled for `get_job`, `get_job_by_custom_id`, `get_jobs`, pulled jobs (`active`) and DLQ jobs (`failed`). TCP parsing accepts legacy payloads where the name was stored inside `data`, but always returns `name` and clean user `data` separately.
- `PulledJob` — `SerializedJob` plus `token?`, present only when a pull with an `owner` was issued a lock.
- `JobCounts` — `{ waiting, prioritized, delayed, active, completed, failed, paused, 'waiting-children'? }` (`types/adapter.ts:31-42`). Both backends fill `waiting-children` and apply the paused view.
- `SerializedCron` — `{ name, queue, schedule?, repeatEvery?, nextRun (ISO|null), executions, jobName, priority, timezone (null = UTC), maxLimit (null = unlimited) }` (`types/adapter.ts:63-78`). The embedded serializer accepts the normalized domain `CronJob` (inactive scheduling field `null`) and converts it to `undefined`; the TCP adapter validates the broker's nested `cron` object (`serializeTcpCron`, `backend/tcp/services.ts`) and calls the same `serializeMcpCron`; `nextRun` goes through `isoTime` in both modes, so a legacy cron whose next run is outside the Date range lists with `nextRun: null` instead of failing `list_crons` for every schedule (TCP used to reject the whole reply as invalid). DLQ timestamps use the same helper; so JSON output omits `schedule` for interval crons and `repeatEvery` for pattern crons in both modes and a pre-field broker falls back to `jobName: 'default'`, `priority: 0`.
- `SerializedDlqEntry` — `{ job (state failed), reason, error, attempts[], attemptCount, retryCount, enteredAt (ISO), lastRetryAt, nextRetryAt, expiresAt (ISO|null) }`; `attempts` lists the last `MAX_DLQ_ATTEMPTS_SHOWN = 10` `{ attempt, reason, error, startedAt, failedAt, durationMs }` records and `attemptCount` the total; errors over `MAX_DLQ_ERROR_CHARS = 1000` end with `… [truncated, N chars]` (`backend/dlqView.ts`).
- `SerializedDlqStats` — `{ total, byReason, pendingRetry, expired, oldestEntry, newestEntry }` (the engine's per-queue breakdown is dropped).
- `QueueLimits` — `{ queue, paused, rateLimit: { max, durationMs } | null, rateLimitTtlMs, rateLimited, concurrencyLimit, active, concurrencyMaxed }` (`backend/limitsView.ts`); the broker's `-2` TTL (no rate limit) becomes `null`, and `rateLimited` is `rateLimitTtlMs > 0`.
- `WebhookInfo` — `{ id, url, events[], queue?, enabled }`.
- `WorkerInfo` — `{ id, name, queues[], active, processed, failed, lastHeartbeat }`.
- `FlowNodeResult` — recursive `{ jobId, name, queueName, children? }` (`backend/serializers.ts:55-62`, `types/adapter.ts:113-118`).
- Workflow views (`workflow/views.ts`) — list row `{ id, workflowName, state, currentNodeIndex, waitingFor? (waiting runs only), failureReason, rollbackStatus, parentExecutionId, createdAt, updatedAt, signalEvents[] }`; detail adds `input`, `steps[]`, `signals: [{ event, payload }]`, `resolvedSteps`, `decisions`, `committedAt`, `definitionHash`. `toJsonSafe` (`workflow/jsonSafe.ts`) converts BigInt to string, Date to ISO, Map/Set/bytes/Error to `$type`-tagged objects and cycles to `"[Circular]"`.
- `McpOperation` — `{ tool, queue|null, timestamp, durationMs, success, error|null }`; `McpSummary` — `{ totalInvocations, successCount, failureCount, avgDurationMs, topTools[] }`.
- `HttpHandler` — `{ url, method: 'GET'|'POST'|'PUT'|'DELETE', headers?, body?, timeoutMs? }`; `HandlerConnection` — `{ host?, port?, token? }`.

## Business Logic / Control Flow

**Startup (`bunqueue-mcp`):**

1. `index.ts:89` calls `launch()` (`index.ts:65`), which dynamically `import('./server.js')` and calls `run()` (`index.ts:67-68`). The dynamic import keeps the SDK + zod out of the static graph.
2. If the import throws `ERR_MODULE_NOT_FOUND` (or a "Cannot find module/package" message) mentioning `@modelcontextprotocol/sdk` or `zod`, the guard at `index.ts:72-82` prints an install hint (`bun add @modelcontextprotocol/sdk`) and exits 1. Any other error is printed as `Fatal error: <message>` (the message only, never the stringified error object such as `Error: ...` or `ConfigError: ...`) and exits 1 (`index.ts:84-85`).
3. `run()` (`server.ts:32`) first parses `BUNQUEUE_MCP_TRANSPORT` and the HTTP settings (`transportConfigFromEnv`, `server.ts:34`), so a bad value aborts before the backend opens. It then calls `createBackend()` and constructs `new HttpHandlerRegistry(handlerConnectionFromEnv())` (`server.ts:39`).
4. In embedded mode with `BUNQUEUE_CLOUD_URL` set, the Cloud configuration is resolved first (`loadCloudConfig`, the validated parser shared with the server), so an invalid `BUNQUEUE_CLOUD_*` value aborts before any transport binds. Then `resolveToolSettings(backend)` validates every opt-in variable (toolsets, confirm, threshold, decision model, workflow DB) and prints its notices once (`server.ts:45`). `createMcpServer` builds the first server from those settings; `setupTools` registers the tool groups while recording each `RegisteredTool` and applies the opt-in features (an empty toolset selection or a stale policy throws here). In `http` mode `startHttpTransport` then binds; that first server is never connected. Any error in this block shuts the handler registry and backend down before rethrowing to `Fatal error:` / exit 1 (`server.ts:51-55`).
5. With that Cloud configuration, a `CloudAgent` is created (`CloudAgent.createFromConfig`) and given `getMcpOperations`. **Invariant:** `mcpTracker.getSummary()` is called _before_ `mcpTracker.drain()` because `drain()` empties the buffer (`server.ts:69-70`). Its connection counts report 0; HTTP sessions are not counted.
6. `http`: writes `bunqueue MCP server started (mode: <mode>, transport: http, url: <url>, version: <v>)` to stderr (`server.ts:97-101`; the URL carries the actual port when 0 was requested). `stdio`: connects a `StdioServerTransport` and writes `bunqueue MCP server started (mode: <mode>, version: <v>)` (`server.ts:105-108`).

**Graceful shutdown** (`server.ts:79-95`): on SIGINT/SIGTERM — close the HTTP transport (every session, then `server.stop(false)` with a 5 s grace before a forced stop), stop the `CloudAgent`, shut the handler registry (closes all spawned workers), `backend.shutdown()` (closes pool/FlowProducer/manager), `server.close()`, then `process.exit(0)`. A second signal is ignored; cleanup errors are swallowed.

**Per-tool invocation:** every handler is wrapped by `withErrorHandler(toolName, fn)` (`withErrorHandler.ts:31`). It records `start = Date.now()`, runs `fn`, and on return records an `McpOperation` to `mcpTracker` (queue extracted from `args.queue` or `args.queueName`, `:19`). Thrown errors are caught, recorded with `success: false`, and returned as `{ isError: true, content: [{ text: JSON.stringify({ error }) }] }` (`:48-62`) — so tool errors surface as MCP error results rather than transport failures.

**Backend dispatch:** each tool calls one `McpBackend` method (`types/adapter.ts:121-228`).

- `EmbeddedBackend` calls the matching `QueueManager` method; flow tools lazily instantiate one embedded `FlowProducer` (`backend/embedded/base.ts:11-14`). Notable mappings:
  - `addJob`/`addJobsBulk` pass `admittedJobInput`/`admittedBulkInputs` to `manager.push`/`pushBatch` (`backend/embedded/jobs.ts`): `toJobInput` plus the checks a TCP `PUSH`/`PUSHB` applies before admission (the 10 MB job-data limit, then the shared `validateJobOptions`, see [Job Options Validation](./job-options-validation.md)), with the same messages (`Job data too large (max 10MB)`, bulk `jobs[i]: ...`). zod already bounds every exposed option; this keeps both backends on one definition, and the embedded backend used to admit an oversized payload the TCP broker refuses; lock-aware pulls use `pullWithLock`/`pullBatchWithLock` (`:110-137`); `ack`/`ackBatch`/`fail`/heartbeats forward tokens and `unrecoverable` (`:139-157`).
  - `waitForJobCompletion` registers the completion waiter before reading the state, returns true at once for a completed job (including one completing during the check), and throws `Job not found` when the job is unknown and has no completion record (`backend/embedded/jobs.ts:86-107`).
  - `getProgress` returns live progress for an active job and the stored `progress`/`progressMessage` for any other existing job (`:160-166`).
  - `getJobCounts` applies the shared `pausedView` and adds `waiting-children` (`backend/embedded/queues.ts:26-39`); `getJobs` passes any state through and tags each job with its state (`:15-23`).
  - `getDlqEntries` applies `dlqFilter(query)` to `manager.getDlqEntries`, then slices `limit + 1` (`:87-98`); `getDlqStats` wraps `manager.getDlqStats`; `getQueueLimits` combines `getQueueLimitStatus`, job counts and `isPaused` (`:136-140`).
- `TcpBackend` translates each call to one wire command through three helpers on `TcpBackendBase` (`backend/tcp/base.ts`):
  - `send` (`:56-58`) routes every command through `assertOk` (`backend/tcp/wire.ts:21-27`): the TCP client resolves `ok: false` replies, so `assertOk` throws a `BrokerError` carrying the broker's own message (`<cmd> failed` when it has none). Used by every command whose failure must surface: `PUSH`/`PUSHB` (which also throw when the reply has no id/ids), `ACK`/`ACKB`/`FAIL`, queue control, DLQ, limits, cron add/list, webhooks add/list, workers, monitoring.
  - `sendFlag` (`:65-73`) serves the boolean tools (cancel, promote, progress, update data, priority, move-to-delayed, `ChangeDelay`, discard, `ExtendLock`, job/worker heartbeat, `AddLog`, `CronDelete`, `RemoveWebhook`, `SetWebhookEnabled`, `UnregisterWorker`): `false` only for a negative-outcome rejection (`not found`, `not active`, `not delayed`, `not in queue`, `invalid token`, `cannot move job from state`; `wire.ts:40-41`). A bare "cannot" is deliberately not matched: runtime errors the broker forwards ("Cannot read properties of undefined ...") and validation errors ("A job cannot be its own parent") are thrown like auth and internal errors (`test/repro-mcp-tcp-negative-outcome.test.ts`).
  - `sendLookup` (`:76-83`) returns `null` only for `not found` (`GetJob`, `GetJobByCustomId`, `CronGet`, the `get_progress` fallback); any other rejection, including auth, is thrown.
  - The pool is built with `commandTimeout: MCP_TCP_COMMAND_TIMEOUT_MS = 45 000` (`base.ts:19`, `:28-34`), above the 30 s maximum long-poll of `pull_job`/`pull_job_batch` and `wait_for_job`, so an empty long-poll returns `job: null` instead of `Command timeout`.
  - Flow tools route through a TCP `FlowProducer` created with an explicit `embedded: false` (`base.ts:41-53`): left unset, `BUNQUEUE_EMBEDDED=1` in the environment would commit flows to an in-process engine. The Bun backend receives the atomic `PUSHF` graph contract.
  - Reply field mapping: drain/purge/retry/retry-completed read `count` (`backend/tcp/queues.ts:47-49`, `:103-114`; `RetryDlq` sends the target as `jobId`); `JobHeartbeatB` reads `data.count`; `WaitJob` returns `completed === true` (an unknown id is rejected by the broker and thrown); `AddWebhook` reads `data.webhookId`, `RemoveWebhook` sends `webhookId`, `ListWebhooks` reads `data.webhooks`; `RegisterWorker` reads `data.workerId` and the real counters, `ListWorkers` reads `data.workers` (`backend/tcp/services.ts:94-142`); `GetLogs` reads `data.logs` and `ClearLogs` forwards `keepLogs` (`backend/tcp/monitoring.ts:87-98`); `GetJobCounts` reads `counts` including `waiting-children` (`backend/tcp/queues.ts:24-37`); `getDlqEntries` sends `{ cmd: 'Dlq', filter, count: limit + 1 }` and reads `entries` (`:88-97`); `GetDlqStats` reads `data.stats`; `getQueueLimits` sends `GetQueueLimits`, `GetJobCounts` and `IsPaused` in parallel (`:132-139`).
  - Job commands: `getProgress` falls back to the stored progress from `GetJob` when `GetProgress` reports a negative outcome (`backend/tcp/jobs.ts:109-128`); `changeDelay` sends `ChangeDelay` and `extendLock` the dedicated `ExtendLock` (`:130-136`); `PULL`/`PULLB` add `owner`/`lockTtl` and attach `token`/`tokens[i]` only when the pull had an owner and the token is non-empty (`:139-162`).
  - Monitoring (`backend/tcp/monitoring.ts`): `getStats` sends `Stats` and `Metrics` in parallel and returns the `stats` object without the wire envelope plus `totalPushed`, `totalPulled`, `totalCompleted`, `totalFailed`, `avgLatencyMs`, `avgProcessingMs`, `memoryUsageMb` from `metrics` (`:23-38`); `getMemoryStats` reads `data.collections` from `DashboardOverview`, which carries exactly `QueueManager.getMemoryStats()` (no dedicated command exists, `:62-69`); `getPerQueueStats` uses `DashboardQueues` (`:40-56`); `Prometheus` reads `data.metrics`.

### Streamable HTTP transport

`BUNQUEUE_MCP_TRANSPORT=http` (`httpTransport.ts:52-139`): one `Bun.serve` endpoint path serves POST (JSON-RPC in, SSE-streamed response out), GET (standalone SSE stream) and DELETE (end session). Responses stream rather than return plain JSON, which lets a tool call send server-to-client requests such as the confirmation elicitation. Every request passes, in order (`route`, `:64-92`):

1. **Host / Origin (403).** Accepted `Host` values (`deriveAllowlist`, `httpSecurity.ts:71-89`): `localhost`, `127.0.0.1` and `[::1]` on the bound port when bound to loopback or a wildcard address; the bound host itself unless it is a wildcard (`0.0.0.0`, `::`); and the `BUNQUEUE_MCP_HTTP_ALLOWED_HOSTS` entries (`host` = any port, `host:port` = that port). A `Host` without a port counts as port 80; a missing `Host` is rejected. `Origin` is checked only when present: it must be `http://<accepted host:port>` (default `:80` dropped) or an `ALLOWED_ORIGINS` entry. This is the MCP DNS-rebinding protection; the SDK's own `allowedHosts`/`enableDnsRebindingProtection` transport options are not used (deprecated in the SDK, exact-string matches, and evaluated only once a request reaches a session transport, after routing).
2. **Path (404)** — exact match of `BUNQUEUE_MCP_HTTP_PATH`.
3. **Auth (401)** — when tokens are configured: `Authorization: Bearer <token>` (scheme case-insensitive). The presented token's SHA-256 digest is compared with `timingSafeEqual` against every configured digest (`createTokenGuard`, `httpSecurity.ts:33-52`). The 401 carries `WWW-Authenticate: Bearer realm="bunqueue-mcp"`, plus `error="invalid_token"` for a wrong token.
4. **Method (405)** — only GET, POST, DELETE (`Allow` header set). A browser CORS preflight therefore gets 405, or 401 when tokens are set; no CORS headers are sent.
5. Bun's idle timeout is switched off for this request only (`server.timeout(req, 0)`), so silent SSE streams and long tool calls are not cut at Bun's default.
6. **Session routing.** A request carrying a known `Mcp-Session-Id` goes to that session's transport (GET, POST or DELETE; DELETE ends the session); an unknown id gets 404. Without a session id, only a POST whose body (or batch) contains an `initialize` request opens a session; any other request gets 400, and an unparsable body gets 400 (`-32700`). At the session cap the initialize gets 503 with `Retry-After: 1`; sessions still being opened count toward the cap. An initialize the SDK rejects (406/415/400) leaves no session behind. An exception in the router returns 500 (`-32603`) and logs to stderr. Bodies over `MAX_REQUEST_BODY_BYTES` (4 MiB) are refused by Bun with 413 before the router runs.

Sessions (`HttpSessionRegistry`, `httpSessions.ts:45-166`): an `McpServer` can be connected to one transport only, so each session gets its own server from `createMcpServer` (built from the settings resolved once at startup) and its own `WebStandardStreamableHTTPServerTransport` with a `randomUUID()` session id; all sessions share one backend and one `HttpHandlerRegistry`. A session is active on any inbound message or outbound send, and busy while a client request awaits its response (cleared by the response or `notifications/cancelled`). The sweeper runs every `clamp(floor(TTL / 2), 10 ms, 60 s)` and closes sessions idle for at least the TTL and not busy; a closed session's id then gets 404. `closeAll()` refuses new sessions (503), stops the sweeper and closes every session; a session finishing its initialize during shutdown is closed immediately.

Validation (`resolveHttpConfig`, `transportConfig.ts:83-117`) runs before binding: a non-loopback host (anything outside 127.0.0.0/8, `::1`, `::ffff:127.x`, `localhost`) without `BUNQUEUE_MCP_HTTP_TOKEN` is refused, as is every malformed value (see [Configuration](#configuration)).

### HTTP handlers

**HTTP handler registration** (`register_handler` → `HttpHandlerRegistry.register`, `httpHandler.ts:96`): stops any existing handler on the same queue, then spawns `Worker(queue, httpProcessor(handler), workerOptions())` with `concurrency: 1`. `workerOptions()` (`:142-146`) is `{ embedded: true }` when the registry has no connection and `{ embedded: false, connection: { host, port, token } }` when it has one. `server.ts:39` passes `handlerConnectionFromEnv()` (`:39-48`), which returns `BUNQUEUE_HOST`/`BUNQUEUE_PORT` (`parseInt`)/`BUNQUEUE_TOKEN` when `BUNQUEUE_MODE=tcp` and `undefined` otherwise: in TCP mode handler workers process jobs on the remote broker and the MCP process never opens a local embedded database, even when a data-path variable is set (`test/mcp-bin-tcp-handler.test.ts`). A worker `'error'` listener writes to stderr so an unreachable broker cannot crash the server (`:105-108`). The processor (`:51-88`) opens an `AbortController` with `setTimeout(timeoutMs ?? 30_000)`, issues `fetch(url, init)` (body = `handler.body ?? job.data` for non-GET/DELETE), parses JSON or text by `content-type`, and throws on non-2xx so the job fails and retries through normal worker semantics.

## Opt-in agent features

With none of `BUNQUEUE_MCP_TOOLSETS`, `BUNQUEUE_MCP_CONFIRM`, `BUNQUEUE_MCP_DECISION_PROVIDER` or `BUNQUEUE_MCP_WORKFLOW_DB` set, `setupTools()` returns right after registration (`toolSetup.ts:126`): the opt-in features add no tool, annotation or parameter to the 75-tool list (asserted by `test/mcp-tool-policy.test.ts`).

**Settings resolution (`resolveToolSettings`, `toolSetup.ts:55-81`).** Every opt-in variable is validated once into a `ToolSettings` object (`toolsets`, `confirm`, `threshold`, `decision`, `workflows`), and each startup notice (decision model unused, workflow signal unavailable, workflow queue ignored) is printed once. `setupTools` and `createMcpServer` accept `{ settings }`; the HTTP transport builds every session's server from the same settings, so no notice or workflow-DB check repeats per session (`test/mcp-tool-settings.test.ts`).

**Tool policy (`toolPolicy.ts`).** Every tool has one entry: its toolset, `readOnly`, `destructive` (deletes or irreversibly overwrites data), `idempotent`, `openWorld` (reaches HTTP endpoints: `register_handler`, `add_webhook`), an optional `confirm` rule naming the argument that identifies the target (`queue`, `jobId`, `name`, `id` or `executionId`), and `optional` for tools registered only under an opt-in setting (the three workflow tools). Whenever toolsets, confirmation or a decision model is active, `assertPolicyCoverage()` (`toolsets.ts:57-67`) refuses to start if a registered tool has no policy or a non-optional policy names a missing tool, so a new tool cannot ship unclassified.

**Toolsets (`BUNQUEUE_MCP_TOOLSETS`, `toolsets.ts`).** 12 toolset ids: the 11 always-populated ones in the tool table above plus the optional `workflows` (3 tools, only with `BUNQUEUE_MCP_WORKFLOW_DB`; 2 when `signal_workflow` is not registered, e.g. in embedded mode). The full default list costs about 57 000 characters (≈16 000 tokens, at ≈3.6 characters per token) of context on every request in clients that load every tool (it was ≈31 700 characters, ≈8 500 tokens, with 73 tools before the job-option, lock-token, DLQ, limit and cron parameters). The dynamic catalog (`bunqueue_enable_toolsets` + `bunqueue_call_tool`) costs ≈850 tokens; catalog plus one toolset ≈1 000–4 600 tokens (median ≈1 800; the largest are `flows` ≈3 750 and `jobs` ≈3 150).

- A comma list (e.g. `queues,dlq`) disables every other tool before the transport connects. Disabled tools are absent from `tools/list` and calls to them are rejected by the SDK. Works with every client.
- `dynamic` (optionally followed by toolsets to preload, e.g. `dynamic,monitoring`) disables all tools and registers `bunqueue_enable_toolsets`, whose description embeds the toolset catalog, and `bunqueue_call_tool`. The catalog, the `enable_toolsets` enum and the `find_tools` choices list only toolsets that have at least one registered tool (`availableToolsets`, `toolsets.ts:87-89`). Enabling a toolset calls `RegisteredTool.enable()`, so the SDK emits `notifications/tools/list_changed`; the result also returns each loaded tool's JSON Schema. `bunqueue_call_tool` validates arguments with the tool's own schema (`safeParseAsync`) and invokes the same (possibly guarded) handler, for clients that do not refresh their tool list. With a decision model configured, `bunqueue_find_tools` asks it to choose a toolset (SystemOne `choice` over the catalog) and loads it; a model failure returns an error that points back to `bunqueue_enable_toolsets`. Over HTTP every session has its own server, so enabling a toolset in one session does not affect another.
- The catalog wording is validated on the 11 always-on toolsets with `scripts/mcp-eval/toolset-routing.ts` and its dataset `toolset-routing.json` (72 natural-language requests: 36 development, 36 held-out, including paraphrases and Italian). TypeSafe Jev (`jev-1.13.0`) routed 71 of 72 to the toolset containing the needed tool with an earlier `queues` description (the held-out "list the failed jobs ... page 2" went to `dlq`, a debatable label) and 72 of 72 after that description was changed to name every job state, so the second score is not blind; details in `scripts/mcp-eval/RESULTS.md`. Plain lexical BM25 over the 75 individual tools (`--lexical`) ranks a needed tool first for 11 and in the top 5 for 19 of the 36 held-out requests (53%), which is why no lexical search is offered.
- Unknown toolset names and a static list with no toolset abort startup (`toolsetModeFromEnv`, `toolsets.ts:28-51`). Selecting (or preloading) a toolset that has no tool in this configuration — e.g. `BUNQUEUE_MCP_TOOLSETS=workflows` without `BUNQUEUE_MCP_WORKFLOW_DB` — also aborts startup (`toolsets.ts:121-126`).

**Confirmation (`BUNQUEUE_MCP_CONFIRM=destructive`, `confirmGuard.ts`).** Every tool gets MCP annotations (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`). Ten tools are guarded because they lose data irreversibly, re-run already completed work in bulk, or deliver an irrevocable approval (bulk `retry_dlq` re-runs failed jobs, the normal remedy for a failure, and is not guarded): `obliterate_queue`, `drain_queue`, `clean_queue`, `purge_dlq`, `cancel_job`, `clear_job_logs`, `delete_cron`, `remove_webhook`, `retry_completed` without `jobId`, and `signal_workflow` (target `executionId`; only when the workflow tools are enabled and the signal tool is registered). Their schema gains an optional `confirm` string and their handler is wrapped (`applyConfirmGuard`, `confirmGuard.ts:168-212`; `gate`, `:103-165`):

1. `describeImpact()` (`confirmImpact.ts:33-100`) builds a concrete preview from the backend: obliterate lists every count including `paused` and `waiting-children` when non-zero; drain lists waiting, prioritized, delayed and `paused`; clean names the state (`completed and failed` when omitted), `graceMs` and `limit`; purge states the exact DLQ total from `getDlqStats`; `retry_completed` the completed count; cancel/clear-logs the job name, state and queue (and `keepLogs`); delete-cron the schedule and queue; remove-webhook the URL; `signal_workflow` the event, a payload preview (500 characters), the workflow name, its state, node index and awaited event, and that the first signal wins, cannot be undone and also opens any later `waitFor` with the same event (`workflow/signal.ts:119-137`). `discard_job` is not guarded: it moves the job to the DLQ, where it can be retried. A lookup failure falls back to `Run <tool> with <args>.`; it never blocks the gate.
2. If the client declared the `elicitation` capability, the server asks the user (form with a `confirm` boolean). The request carries the triggering tool call's id (`relatedRequestId`), so over Streamable HTTP it travels on that call's POST response stream and reaches clients that never open the optional standalone GET stream (`test/repro-mcp-http-elicitation.test.ts`). Only `accept` with `confirm: true` runs the tool; decline, cancel or an elicitation error refuse it, even when the agent also passed `confirm`.
3. Otherwise the agent must pass `confirm` equal to the target (queue name, job id, cron name, webhook id or execution id). A missing or different value returns `isError` with `executed: false`, the impact and `howToConfirm` instructions. The refusal reads `Confirmation required for a destructive operation.` for destructive tools and `Confirmation required for this operation.` for the non-destructive guarded ones (`retry_completed` in bulk, `signal_workflow`).
4. With a decision model configured, the guarded schema also gains `userRequest`, and step 3 additionally requires the user's verbatim request; the model (SystemOne `noul`) must judge with probability ≥ `BUNQUEUE_MCP_DECISION_THRESHOLD` (default 0.8) that it explicitly asks for exactly this operation. The model can only block: it is not consulted after an elicitation answer, and any transport, HTTP or format error refuses the call (fail closed).

Refusals bypass `withErrorHandler`, so they are not recorded as tool executions in `mcpTracker`.

**Decision models (`decisionModel.ts`).** One client speaks the SystemOne format (`POST { model, state, questions }` → `{ answers }`) used by all supported models: `BUNQUEUE_MCP_DECISION_PROVIDER=typesafe` (TypeSafe Jev, default model `jev-latest`, `https://api.typesafe.ai/v1/systemone`), `cloudflare` (Clef / Clef-flash on Workers AI, default `clef-flash`, URL built from `BUNQUEUE_MCP_DECISION_ACCOUNT_ID`; the `{ result }` envelope is unwrapped) or `systemone` (any compatible endpoint such as a self-hosted Clef, Clef-flash, Kev 9B, Laya or DiffusionGemma Jev; URL and model required, key optional). Requests send `Authorization: Bearer` when a key is set, time out after `BUNQUEUE_MCP_DECISION_TIMEOUT_MS` (default 10000) and are retried once on network errors, timeouts, 429, 500, 502, 503 and 529. Answers are validated (`choice` must be one of the offered ids, `noul` a finite number). No request is made from the job path; only `bunqueue_find_tools` and the confirmation gate call the model. Data sent: `find_tools` sends the agent's request and the toolset catalog; the gate sends the user's `userRequest` and the impact text (queue/job/cron/webhook names and counts; for `signal_workflow` also the payload preview of at most 500 characters). Job payloads are never sent otherwise. The confirmation binds the target argument only; the other arguments of the confirmed call are the ones the impact text describes. When a model is configured but neither feature is enabled, startup writes a warning to stderr.

**Workflow tools (`BUNQUEUE_MCP_WORKFLOW_DB`, `workflow/`, `tools/workflowTools.ts`).** `workflowToolsFromEnv` (`workflow/config.ts:32-65`) resolves the path against the MCP process cwd and requires an existing regular file that opens as SQLite and holds a `workflow_executions` table; anything else aborts startup (the MCP server never creates a workflow database). `BUNQUEUE_MCP_WORKFLOW_QUEUE` (default `__wf:steps`) must equal the Engine's `queueName`; set without the DB it only prints a stderr notice.

- **Store access** (`WorkflowDb`, `workflow/workflowDb.ts`): the MCP never constructs `WorkflowStore` (its constructor runs DDL/migrations). Every call opens the existing file read-write without the create flag, sets `busy_timeout = 5000`, runs, and closes with `close(true)`, which finalizes the prepared statements of the engine helpers so the connection and its db/-wal/-shm handles are released at once (`:95-108`; plain `close()` left them open until garbage collection, `test/repro-mcp-workflow-db-handles.test.ts`). A long-lived connection is avoided on purpose: bun:sqlite fixes a prepared statement's result columns on first run, so an Engine schema migration while the MCP server runs would silently drop new columns. Reads reuse `decodeExecution` and `ExecutionListing`; signals reuse `SignalCoordinator.record`/`restoreWaiting`, so an MCP signal takes the same IMMEDIATE, first-writer-wins transaction as `engine.signal()`. The process needs write access to the file, its `-wal`/`-shm` files and the directory.
- **`list_workflow_executions`** (`workflowName?`, `state?` ∈ `running|waiting|completed|failed|compensating|compensation-stuck`, `limit?` 1–1000 default 50, `offset?` ≥ 0) returns `{ executions, count, limit, offset, nextOffset }`, newest first; `nextOffset` is `null` once a page comes back short. **`get_workflow_execution`** (`executionId`) returns the detail view or an `isError` not-found result. Node names are unknown to the MCP server (definitions live in the application), so nodes are reported by index.
- **`waitingFor`** (`awaitedEvent`, `workflow/views.ts:23-30`) is known only for timed gates, which persist a `__waitFor:<event>` record; it is the single running record whose signal is absent. Untimed gates leave no record, so `waitingFor` is `null`.
- **`signal_workflow`** (`executionId`, `event`, `payload?`; `deliverSignal`, `workflow/signal.ts:49-110`), mirroring `signalExecution`: (1) reject an unusable event name (`unusableEventName`); (2) load the execution (`not found` → error) and, when a timed gate is waiting for a different event, refuse without recording (a stricter check than the engine: a wrong name would silently pre-open a later `waitFor` of that name); (3) `SignalCoordinator.record` — a duplicate signal or a run that is not `running`/`waiting` throws; (4) if the record did not claim a resume, return `{ recorded: true, resumed: false, note }` (the signal opens the gate when the run reaches it); (5) if it did, `backend.addJob(queue, 'wf:step', { executionId, workflowName, nodeIndex }, { removeOnComplete: true })` — `removeOnComplete` matches the Engine's own step jobs, so nothing is retained on the broker — and return `{ recorded, resumed: true, executionId, workflowName, event, nodeIndex, queue, jobId }`; (6) if enqueueing fails, `restoreSignalWait` puts the wait back (the signal stays recorded) and the tool returns `isError` with `{ recorded: true, resumed: false, restored, error, next }`; the application's `engine.recover()` or the gate's timeout re-check re-drives the run. The MCP process never runs steps, compensations or recovery. Policy: write, not idempotent, not destructive, not open-world, confirm target `executionId`.
- **Supported topology.** The application's `Engine` connects over TCP to a bunqueue server and has its own `dataPath`; the MCP runs with `BUNQUEUE_MODE=tcp` against the same server and queue name and can open the same file on the same host (SQLite over NFS is unsafe). `signal_workflow` is not registered (stderr explains why) when the MCP backend is embedded — the resume job would land in its own in-process queue — or when the file also holds bunqueue's `jobs` table, which means an embedded Engine whose step queue lives inside the application process. List and get still work in both cases.

## Concurrency & Locking

The MCP server holds no locks of its own; concurrency safety is delegated to the backend ([Concurrency & Locking](./concurrency-and-locking.md) for embedded, TCP server for remote). Notable points:

- `mcpTracker` is a single-threaded in-process singleton (no locking needed); `record` and `drain` mutate one array (`mcpTracker.ts:44-54`). Over HTTP every session records into the same tracker.
- HTTP sessions share one backend (one embedded `QueueManager` or one TCP pool), one `HttpHandlerRegistry` and one decision-model client. Each session has its own `McpServer` and `RegisteredTool` map, so dynamic toolset state is per session, while handlers are process-wide: a handler registered in one session is listed, replaced or removed by any other session.
- HTTP handlers run as real `Worker`s with `concurrency: 1` per queue, participating in normal lock-based job ownership; lease/heartbeat behavior is the Worker's, not the MCP layer's.
- `extend_lock`/`job_heartbeat` forward to the lock/heartbeat machinery: TCP sends the dedicated `ExtendLock` command (`backend/tcp/jobs.ts:134-136`) and `JobHeartbeat` with the optional `token` (`:182-184`); the embedded path calls `manager.extendLock(id, token, duration)` and `manager.jobHeartbeat(id, token)` (`backend/embedded/jobs.ts:151-174`).
- Workflow signals are arbitrated in SQLite, not in the MCP process: `SignalCoordinator.record` and the Engine's gate-expiry claim (`WorkflowStore.expireWait`, `src/client/workflow/storeWaitExpiry.ts`) take the same IMMEDIATE write reservation, so a signal and a timeout cannot both win. The MCP's awaited-event pre-check runs before that transaction and is advisory; the transaction is authoritative.

## Edge Cases & Failure Modes

- **Optional SDK absent:** handled with an actionable install hint and exit 1 (`index.ts:72-82`).
- **Invalid configuration:** every `BUNQUEUE_MCP_*` value is validated at startup; a bad value prints `Fatal error:` and exits 1 before anything binds. Transport settings fail before the backend opens; a later failure (tool settings, server build, a busy HTTP port) first shuts the handler registry and backend down (`server.ts:51-55`).
- **Telemetry buffer bound:** `mcpTracker` is a ring buffer capped at `MAX_BUFFER_SIZE = 200`; at capacity each `record` does `Array.shift()` (O(n) but n≤200, ~40KB max, `mcpTracker.ts:44-49`). If no `CloudAgent` consumer drains it, the buffer self-bounds by evicting oldest.
- **Tool errors are non-fatal:** `withErrorHandler` converts thrown errors to `isError` results; `extractErrorText` truncates raw non-JSON error text to 200 chars (`withErrorHandler.ts:77`). Over TCP the error text is the broker's own message (`BrokerError`).
- **Not-found results:** `get_job`, `get_job_by_custom_id`, `get_progress`, `get_flow`, `get_cron`, `get_workflow_execution` return `{ isError: true, error: '...not found' }` rather than throwing; `wait_for_job` on an unknown id throws `Job not found`. Boolean tools return `success: false` for a missing target or wrong state.
- **Pagination translation (issue #87):** the MCP `get_jobs` tool exposes `start`/`end`, but the TCP protocol uses `offset`/`limit`; `TcpBackend.getJobs` translates `limit = end - start` (`backend/tcp/queues.ts:9-22`) so pagination actually applies in TCP mode.
- **Per-queue stats (issue #87):** `TcpBackend.getPerQueueStats` queries `DashboardQueues` (not `Metrics`) to get a real per-queue breakdown (`backend/tcp/monitoring.ts:40-56`).
- **`get_stats` differs by backend:** embedded returns `waiting`, `prioritized`, `delayed`, `active`, `dlq`, `completed`, `waiting-children`, `totalPushed`, `totalPulled`, `totalCompleted`, `totalFailed`, `uptime`, `cronJobs`, `cronPending` (BigInt counters converted to numbers by a `JSON.stringify` replacer, `backend/embedded/services.ts:92-101`). TCP returns the broker's `Stats` object (`waiting`, `active`, `delayed`, `dlq`, `completed`, `failed`, `uptime`, `pushPerSec`, `pullPerSec`) plus the `Metrics` totals listed above; it has no `prioritized`, `waiting-children`, `cronJobs` or `cronPending`.
- **Paused queues:** both backends report a paused queue's ready jobs only under `paused` (shared `pausedView`), so counts, `count_jobs` and the drain/obliterate previews never double-count.
- **Storage-health redaction:** the embedded backend applies the same
  `clientStorageStatus` projection as the TCP server. Non-disk SQL/network
  diagnostics never enter an MCP tool result; SQLite disk-full keeps its
  actionable error. The TCP backend inherits the projection from the
  `StorageStatus` command (`backend/tcp/monitoring.ts:79-85`).
- **Cron null normalization:** the domain and TCP protocol intentionally retain
  `null` for the inactive cron scheduling field, while the MCP
  `SerializedCron` contract uses optional fields. Both backends normalize the
  boundary to `undefined`; regression coverage exercises `add`, `list` and
  `get` for interval and pattern crons against embedded and a real TCP broker.
  The same shared contract also runs explicitly in both functional matrices via
  `scripts/embedded/test-mcp-cron-serialization.ts` and
  `scripts/tcp/test-mcp-cron-serialization.ts`, including metadata, deletion
  and post-delete lookup behavior.
- **Cron replies:** `{ ok: false, error }` is thrown with the broker error (`assertOk`) instead of being converted into fabricated cron metadata; a successful reply must contain a valid nested `cron` object, otherwise `Invalid cron response from broker`. `get_cron` returns `null` only for `Cron job not found`; auth and other errors are thrown.
- **Cron options not echoed (known limitation):** `skipIfNoWorker`, `preventOverlap`, `skipMissedOnRestart`, `deduplication` and the job options are applied end to end in both modes but are not returned by `add_cron`, `list_crons` or `get_cron`: the broker's cron reply (`cronData`, `src/infrastructure/server/handlers/cron.ts:21-34`) does not carry them, and the embedded serializer reports the same fields to keep the modes identical.
- **DLQ output (breaking change):** `get_dlq` returns `entries` with the job nested in each entry; clients that read the former top-level `jobs` array must switch to `entries[].job`. Malformed broker entries/stats throw `Invalid DLQ ... from broker`.
- **Rate-limit TTL ambiguity:** the broker's `rateLimitTtl` is either the time until the bucket admits the next job or the time until a temporary client-set limit expires; the reply does not say which, and `get_queue_limits` reports it as `rateLimitTtlMs` unchanged.
- **Concurrency limit set under load (known engine issue, not fixed):** setting a concurrency limit while jobs are already active starts the limiter at 0 (`setConcurrency`, `src/domain/queue/limiterManager.ts`), so the queue can exceed the limit until those jobs finish (with 2 active and limit 2, `concurrencyMaxed` is `false` and a third pull succeeds). `get_queue_limits` reports the broker's state faithfully.
- **Stricter inputs:** non-integer or < 1 rate/concurrency limits, empty queue/job/cron names (including `get_cron`/`delete_cron`), delays over one year (`move_to_delayed`, `change_delay`), non-integer or out-of-range `clean_queue` `limit`, `get_jobs` `start`/`end` and `get_flow` `depth`/`maxChildren`, non-integer `repeatEvery`, unknown time zones, a `timezone` without `schedule`, unknown flow `opts` keys, malformed Unicode in ids/keys/tags and `lockTtl` without `owner` are rejected before reaching either backend, so nothing is applied.
- **HTTP handler single-per-queue:** registering a handler on a queue that already has one silently `unregister`s the previous worker first (`httpHandler.ts:98-100`); only one handler per queue can be active.
- **HTTP handler timeout:** request aborts via `AbortController` after `timeoutMs` (default 30s; tool schema clamps 1000–120000ms); the timer is always cleared in `finally` (`httpHandler.ts:84-86`).
- **Webhook event validation:** `add_webhook` accepts only `WEBHOOK_EVENTS` (`job.pushed|started|completed|failed|progress`); `job.stalled` is accepted by stored types for backward-compat but is never emitted.
- **Tool input bounds:** `wait_for_job` timeout 100–30000ms; `pull_job`/`pull_job_batch` timeout 0–30000ms with `count` 1–1000; `update_progress` 0–100; `get_dlq` `limit` 1–100; `list_workflow_executions` `limit` 1–1000.
- **Workflow tools:** if the MCP is not connected to the server the Engine consumes, or the queue name differs, the run is flipped to `running` and its resume job sits on the wrong queue until the application calls `recover()`; neither mismatch is detectable. The application's `signal:received` listeners do not fire for MCP signals (later step and workflow events do), and the Engine's timeout timer is not cleared — it fires later as a harmless re-check.
- **HTTP transport limitations:** no built-in TLS (use a reverse proxy; its `Host` and any browser `https://` origin must be allowed explicitly); no stream resumption, so a dropped SSE stream loses in-flight messages; sessions live in memory and end on restart (clients get 404 and must re-initialize); no stateless mode, and one standalone GET stream per session (the SDK answers a second with 409); the 413 response has an empty body rather than a JSON-RPC error; tokens cannot contain commas or whitespace; bound to `0.0.0.0`, only loopback names pass the Host check, so LAN names or IPs must be listed in `BUNQUEUE_MCP_HTTP_ALLOWED_HOSTS`; an authenticated client keeps its session alive by sending traffic, and a request whose handler never answers keeps its session busy (the session cap still applies). IPv6 binding is not covered by tests.
